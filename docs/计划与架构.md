## 1. 技术选型与依据

| 层 | 选择 | 依据 |
| --- | --- | --- |
| 核心 | Rust（tokio + rustls 0.23） | 内存安全、流式性能、Windows/Linux/Android 一套核心；rustls 纯 Rust 实现 TLS 1.3，不依赖沙箱内不可用的 Schannel |
| 身份 | Ed25519 长期密钥 + 自签名 X.509 证书（rcgen） | 成熟库；设备身份绑定密钥，SPKI 指纹用于信任比对 |
| 传输安全 | TLS 1.3 mutual-TLS（只开 1.3，禁 1.2） | rustls 已通过广泛审计；不自研加密算法 |
| 记录存储 | SQLite（rusqlite bundled）+ 应用层 AES-256-GCM 逐记录加密 | 结构可靠；密钥单独存放，数据文件内无明文 |
| 导出/导入 | 独立密码 + Argon2id 派生 + AES-256-GCM 信封 | 用户已确认：独立密码、仅消息与记录 |
| UI | Flutter（全新界面，Windows/Linux/Android 一套代码） | 非 Web 壳；一套代码三平台；动画系统适合目标交互质感 |
| 桥接 | flutter_rust_bridge v2 | 成熟的双向 FFI 方案，核心可脱离 UI 运行 |
| 无头测试 | lunote-cli（Rust） | 核心自动化与网络回归测试入口，不依赖 UI |
| 发现协议 | 从 lanprobe 迁移：UDP 组播 239.255.77.77 + 有限广播 + 子网定向广播 | 已真实验证；保留版本字段并增强容错 |

## 2. 架构

```
┌────────────────────────────────────────────────┐
│  Flutter UI（Windows / Linux / Android）        │  只消费核心事件；无假设备
│  └ 设备列表 / 对话 / 传输中心 / 信任确认 / 设置   │
└───────────────┬────────────────────────────────┘
                │ flutter_rust_bridge (FFI)
┌───────────────▼────────────────────────────────┐
│  lunote-core（Rust，可脱离 UI 独立运行）         │
│  discovery → identity → trust → session(TLS1.3) │
│  → messages → transfer(流式) → store(加密)      │
│  events(事件总线)   runtime(生命周期/节流)        │
└───────────────┬────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────┐
│  lunote-cli：serve / pair / send / export ...   │  自动化与回归测试
└────────────────────────────────────────────────┘
```

关键边界：

- 设备列表只来自 `discovery` 的真实 UDP 信标；UI 不得自行维护设备列表。
- 身份与信任由 `identity` / `trust` 持久化管理；首次信任需用户确认（按钮确认 +
  指纹展示，按用户选择）；未信任设备可发文字/链接，文件传输必须信任且逐次确认。
- 所有传输经 TLS 1.3 双向认证通道；文件流式读写（固定块 + 双缓冲），SHA-256
  增量校验，临时文件 + 原子改名，路径净化防目录穿越。
- 聊天与传输记录加密落盘；导出用独立密码（Argon2id + AES-256-GCM），导入去重。

## 3. 发现协议（正式版 LUNOTE1）

保留版本字段，一行 UTF-8 文本（名称百分号编码）：

```
LUNOTE1|ver=1|name=<编码名>|dev=<设备ID>|inst=<实例ID>|seq=<序号>|ts=<毫秒>|port=<端口>
```

与 lanprobe 的 PROBE1 相比，正式核心额外处理：

- 协议版本校验与“未知版本”降级策略（记录日志，不误判为设备）；
- 错误/畸形数据包统计与忽略；
- 重复数据包（seq 去重）；
- 设备重启（同 device_id 新 instance_id → 替换旧实例并保留信任关系）；
- 同名设备（以 device_id 区分，不合并）；
- 多网卡（逐接口组播 + 每接口子网广播；同一设备经多接口出现时归并到主地址）；
- 改名（同 instance_id 名称变化 → 更新显示名，设备身份不变）；
- 离线超时（基于真实信标到达时间）；
- 网络变化自动恢复（接口枚举失败时重试 + 周期重发）；
- 后台节流（无任务时降低信标频率，保留接收能力）。

## 4. 安全模型（摘要，详见 docs/安全模型.md）

- 设备长期身份：Ed25519 密钥对；密钥文件权限 0600（Windows 下可选 DPAPI 包裹，
  Android 下位于应用私有目录），不写明文到配置。
- 连接认证：TLS 1.3 mutual-TLS；对端证书 SPKI 指纹必须与信任库/TOFU 记录一致，
  否则握手失败并报告身份变化（警告而非静默接受）。
- 首次信任：TOFU + 用户按钮确认；界面同时展示短指纹供人工核对；确认后指纹
  永久绑定 device_id，身份变化即告警。
- 陌生人策略（用户已确认）：陌生设备可发起连接并发送文字/链接（通道仍加密且
  身份可追踪）；发送文件必须已信任 + 接收方逐次确认。
- 传输完整性：全量 SHA-256（发送端与接收端独立计算比对）+ 分块计数 + 文件大小
  核对；断点续传时校验已接收部分哈希后接续。
- 本地记录：逐条 AES-256-GCM（随机 nonce）；主密钥与身份密钥同源管理；
  数据文件内无明文消息/文件名/链接。
- 导出：Argon2id(密码) → AES-256-GCM 信封，含元数据与校验；导入校验完整性，
  按消息 UUID 去重；导出文件丢失 = 不可解密（安全边界如实说明）。
- 已知边界（不夸大）：局域网内物理攻击者可能进行泛洪/窃听发现报文（发现阶段
  不携带敏感内容）；确认按钮方案对“视觉无法核对指纹”的用户存在冒充风险，
  文档中如实说明并建议核对短指纹。

## 5. 实施阶段

1. 骨架与工具链（本阶段）：新项目结构、cargo 依赖拉取、Flutter SDK 安装、
   JDK/Python 工作区副本、Android 构建链验证。
2. 发现生产化：Rust 实现 LUNOTE1，单元测试 + 本机双实例真实回环测试 +
   Rust↔Python(probe) 互操作回归（python 可运行后）。
3. 身份与信任：密钥生成/持久化/证书签发、信任库 CRUD、TOFU 记录。
4. TLS 1.3 会话：双向认证握手、帧协议、心跳、断线检测；文字/链接消息。
5. 文件传输：offer/接受/拒绝、流式分块、完整性、取消、重试、断点续传、
   文件夹清单、路径净化、同名与剩余空间处理。
6. 加密记录：SQLite 落库加密、查询、导出/导入、去重、彻底删除。
7. Flutter UI：全新视觉体系（柔软弹簧交互）、设备/对话/传输/信任/设置/托盘、
   拖放、后台节流；只消费核心事件。
8. 平台构建：Windows 可运行程序；Android APK；Linux 构建配置（本机无法构建
   桌面 Linux 二进制时如实标注，提供 CI 与交叉编译产物）。
9. 验证与交付：自动化测试、回归脚本、原始日志归档、文档、分平台验证报告。

## 7. 已确认的产品决策（用户拍板，2026-08-16）

- 首次信任：按钮确认 + 指纹展示（用户选择“仅按钮确认”，文档如实标注风险）。
- 陌生设备：可发文字/链接；文件必须信任 + 逐次确认。
- 记录导出：独立密码（Argon2id + AES-256-GCM），仅消息与记录，不含文件本体。
- 第一阶段：仅一对一对话（协议预留多设备字段）。
- Android 后台：遵守系统规则，前台/传输时用前台服务，不做偷偷保活。
