# 月笺 Lunote 安全模型

> 本文档如实描述已实现的安全机制及其边界。不使用“绝对无法破解”等无法证明的表述。

## 1. 威胁模型

- 防御对象：同一局域网内的被动窃听者、主动攻击者（冒充、篡改、重放）、
  恶意设备发送有害内容、本地磁盘被直接读取、导出文件泄露。
- 明确不在范围内的边界：国家级攻击者、已被攻陷的操作系统、物理接触设备的
  攻击者（可读取内存/密钥文件）、发现阶段的局域网泛洪。

## 2. 传输安全（已实现）

- 所有文字、链接、文件控制消息、文件数据都走 **TLS 1.3**（rustls + ring，
  仅启用 1.3，禁 1.2/1.1）。不依赖操作系统 Schannel。
- 双向认证：双方各持有 Ed25519 长期密钥 + 自签名 X.509 证书。
  - rustls 层对证书做结构校验（自管信任模型，信任锚是“设备指纹”，不是 CA 层级）；
  - **应用层签名挑战**：服务端先发 32 字节随机 challenge，客户端回
    `Hello`（证书 + 对 challenge‖device_id‖name‖instance_id 的 Ed25519 签名），
    服务端回 `HelloAck`（同样结构）。挑战每次连接随机 → 防重放；
  - 证书指纹 = SHA-256(证书 DER)。指纹与 TOFU 记录/信任库比对：
    - `New`：首次见面，自动记录指纹（TOFU）；
    - `Same`：与记录一致，正常；
    - `Changed`：同一 device_id 出现不同指纹 → 发出身份变化警告事件，
      并降级为不可信（不能发文件）。
- 信道内每个连接重新协商密钥；无会话恢复（无 PSK），避免重放。
- 心跳 Ping/Pong 与空闲超时（60 秒）防止僵尸连接。

### 如实说明的边界

- 首次信任采用“按钮确认 + 指纹展示”。TOFU 记录自动建立后，若用户不核对
  指纹就确认，局域网内抢先冒充的设备可能建立假信任——这是所有 TOFU 方案的
  固有权衡，界面会展示可人工核对的短指纹，文档建议核对。
- **同名同 IP 自动信任（默认开，设置页可关）**：新设备与已信任设备“同名且
  同 IP”时自动信任，免去重复确认。设备名与 IP 在局域网内可被伪造（如抢 IP、
  改名），自动信任使“已信任设备被替换”时的冒充门槛降低——仅建议在家庭/
  可信局域网开启；公共网络建议在设置页关闭。自动信任事件带 `auto_trusted`
  标记，UI 会提示“已自动信任”，用户可随时关闭。
- rustls 层不校验握手签名（`accept-any` 验证器），身份绑定完全依赖应用层
  签名挑战。由于挑战覆盖了设备标识且每次新鲜，冒充者无法在已知设备的
  会话中伪造身份；对“全新设备”的首次冒充属于 TOFU 固有风险。
- 发现信标（UDP）本身不加密且包含设备名：这是局域网可见的最小信息，
  发现阶段不携带任何消息内容。攻击者可伪造信标造成假在线/离线（拒绝服务），
  但不能借此读取或篡改会话内容。

## 3. 设备身份与密钥存储

- 身份：Ed25519 密钥 + 自签名证书，首次启动生成，之后永久不变（文件：
  `identity.key` 32 字节种子、`identity.json` 元数据）。
- 权限：Unix 下密钥文件 `0600`；Windows 依赖用户目录 ACL。
- 未实现（后续改进，如实）：Windows DPAPI 包裹密钥、Android Keystore、
  Linux Secret Service。当前 Android 上密钥位于应用私有目录（无 root 不可读）。
- 设备改名不影响身份与信任关系。

## 4. 信任管理（用户已确认的策略）

- 未信任设备：自动出现在设备列表；可建立加密会话并发送**文字/链接**；
  发送**文件**会被自动拒绝（“未信任设备不能发送文件”）。
- 可信设备：用户从设备列表/对话中一键确认信任（界面显示指纹短码）；
  可双向发送文件；接收文件仍需要接收方**逐次确认**（保存位置）。
- 解除信任 / 删除设备：立即生效，再次连接需重新确认。
- 身份变化：自动警告 + 降级，需要用户重新确认。

## 5. 文件传输安全

- 完整性：收发双方独立增量 SHA-256，完成时比对（大小 + 哈希双重校验）；
  不匹配 → 失败并删除临时文件，不产生半成品最终文件。
- 断点续传：接收端校验已收部分哈希后接续；部分哈希不一致 → 从头重传。
- 路径安全：文件名/相对路径净化（拒绝绝对路径、`..`、控制字符），
  防止目录穿越；接收端先检查剩余空间。
- 落盘安全：`.part` 临时文件 + 校验通过后原子改名；进程中断不会产生
  被误认为完整文件的残留。
- 发送端文件在传输中变化：按初始大小传输，完成时哈希按实际发送内容计算，
  接收端大小校验失败会如实报错（不会静默产出错误文件）。

## 6. 本地记录（已实现）

- 存储：SQLite（`records.db`）+ **逐记录 AES-256-GCM**（每条消息随机 nonce）。
  数据文件内无明文消息、链接、文件名。
- 密钥：32 字节随机主密钥 `records.key`（0600）。密钥丢失 = 记录不可恢复。
- 数据库结构（会话名、时间戳）不加密（元数据泄露面如实说明：攻击者可看到
  与谁对话、何时对话，看不到内容）。

## 7. 导出 / 导入（用户已确认：独立密码、仅记录）

- 导出文件格式：`LUNOTEXP1` 魔数 + 版本 + Argon2id（64 MiB / t=3 / p=1，
  独立密码派生 KEK）→ 随机 DEK 包裹 → AES-256-GCM 加密 JSON（仅消息与
  传输记录，不含文件本体）。
- 导入：GCM 标签校验完整性（密码错误或文件被篡改都会失败）；按消息 UUID
  去重；重复导入不产生重复记录。
- 安全边界：导出文件丢失/密码遗忘 = 无法解密；导出文件是自包含加密容器，
  可离线验证（重新导入即验证）。

## 8. 审计与更新

- 依赖：rustls（ring）、ed25519-dalek、aes-gcm、argon2、sha2、rcgen、
  rusqlite 均为成熟公开库；不自研加密算法。
- 密钥/证书轮换、前向安全增强（每连接 ECDHE 由 TLS 1.3 提供）、
  Android Keystore 绑定等列入后续改进。
